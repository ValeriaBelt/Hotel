# Inicio de sesión seguro de administradores

El backend HTTPS sirve la aplicación web y la API. Para abrirla directamente, inicia el backend y visita `https://localhost:3443/`. En desarrollo, también expone la API por HTTP en `http://localhost:3000`, enlazada solo a localhost. Así puedes abrir primero el backend con `npm start` y luego abrir `frontend/index.html` con VS Code Live Server, sin visitar manualmente la URL HTTPS ni aceptar su certificado local.

Al usar Live Server, las páginas detectan automáticamente su origen local y envían las peticiones a `http://localhost:3000`. El acceso HTTP solo se activa cuando `NODE_ENV` no es `production`; el servidor HTTPS sigue disponible. El puerto predeterminado de Live Server, `5500`, está autorizado. Si usas otro puerto, añádelo a `HOTEL_CORS_ORIGINS` como un origen completo antes de iniciar el backend.

En el primer inicio de sesión de cada administrador, se mostrará una clave secreta una sola vez. Añádela manualmente a una aplicación compatible con TOTP y confirma el código de seis dígitos para completar la configuración. Los inicios de sesión posteriores solicitan el código actual.

Las contraseñas existentes en texto plano se convierten a PBKDF2 al comprobar correctamente la contraseña. Las nuevas cuentas se guardan con hash y requieren una contraseña de al menos 12 caracteres. Después de tres fallos de contraseña o MFA, la cuenta se bloquea durante 30 segundos.

El panel aplica RBAC con los perfiles `Administrador` y `Operador`. Administrador tiene acceso completo, incluida la administración de perfiles y la bitácora; Operador puede gestionar habitaciones y reservas, pero no puede administrar usuarios ni consultar la bitácora. Los registros existentes reciben el rol Administrador al iniciar el backend por primera vez tras la actualización. Al crear un perfil, se debe asignar explícitamente uno de esos roles. Los Administradores pueden cambiar el rol de otros perfiles desde la lista; no pueden cambiar el rol de su propia sesión. Al cambiar o eliminar un perfil se revocan sus sesiones activas y retos MFA pendientes. El perfil debe volver a iniciar sesión para obtener los permisos vigentes. El panel muestra el rol de la sesión y una lista de perfiles, visible solo para Administradores.

El backend crea las tablas `AdminSecurity` y `AdminSecurityAudit` si aún no existen. La clave de cifrado MFA se genera y conserva en `backend/security/hotel-mfa.key` para el entorno local; no la elimines ni la compartas, porque se necesita para descifrar los secretos TOTP ya registrados. Mantén la misma clave mientras haya MFA configurado. En producción, configura `HOTEL_MFA_ENCRYPTION_KEY` con una clave de 32 bytes codificada en hexadecimal (64 caracteres) y resguárdala en el gestor de secretos del entorno.

Los cambios de habitaciones y la gestión de administradores requieren una sesión autenticada. La búsqueda y cancelación de reservas desde el panel requieren el rol `Administrador` u `Operador`; además, toda cancelación —también la realizada por personal— exige el código de gestión de esa reserva. El backend comprueba el código asociado al ID y no permite cancelar únicamente con correo, teléfono o ID. Buscar reservas ya no expone datos de clientes públicamente. Las sesiones usan una cookie `HttpOnly` y `Secure`; las solicitudes administrativas que modifican datos también validan el origen permitido para proteger contra CSRF. Las sesiones se invalidan al reiniciar el servidor.

La creación pública de reservas continúa disponible. Tras crear una reserva, se muestra una sola vez un código de gestión aleatorio; guárdalo y no lo compartas para consultar o cancelar la reserva desde `ReservasCliente.html`. El personal que crea una reserva desde el panel debe entregar ese código al cliente. El servidor conserva únicamente el hash del código. El correo o el teléfono no bastan para consultar datos ni cancelar, tampoco por parte del personal. Si se pierde el código, debe contactarse con el hotel para seguir un proceso de verificación de identidad independiente; no se debe cancelar basándose solo en correo o teléfono. Las reservas creadas antes de esta mejora no tienen código y no se pueden cancelar desde el autoservicio ni el panel hasta completar ese proceso de verificación.

Las fechas, habitación y datos de contacto se validan en el backend. La creación vuelve a comprobar disponibilidad dentro de una transacción y bloquea la habitación durante esa comprobación para evitar reservas simultáneas incompatibles.

La bitácora identifica la cuenta o perfil objetivo en los intentos fallidos de contraseña y MFA. Cuando el correo no corresponde a una cuenta registrada, muestra el identificador ingresado. Los eventos históricos que no guardaron el perfil objetivo indican que la cuenta no se puede recuperar; si la cuenta asociada fue eliminada, la bitácora lo indica por separado. En los inicios de sesión exitosos y cierres de sesión también muestra el perfil que realizó la acción. Ese dato forma parte de la firma de integridad; los eventos antiguos sin perfil siguen verificándose. La vista se puede filtrar por ataques (fallos de contraseña o MFA), inicios de sesión (verificación MFA, inicio correcto y cierre de sesión) o todos los eventos registrados.

Para ejecutar las pruebas desde `backend`, usa `npm test`.
